- `apps/web/scripts/build-extension.mjs`, `build-mails-auth.mjs`, `src/lib/extension-cad.ts`, `src/lib/handle.ts`, `apps/api/grabador_adsb.py`, `apps/api/.gitignore`: rutas nuevas, y `Charts/` fuera de git.

**Por qué:** desde el 1/10, 10 de cada 13 días con commits tocaron los dos repos, y casi toda feature es "migración N del backend + pantalla". Separados, un cambio de modelo quedaba en dos commits sin revisión conjunta, con dos bitácoras y dos CI. Se descartaron:
- **`frontend/` y `backend/`** (Federico: "queda muy burro"): `apps/` es la convención de los monorepos, y la extensión del CAD es una app más, no una carpeta de la web.
- **Reescribir la historia con `git filter-repo`**: deja `git log apps/api/x` limpio, pero cambia todos los hashes, y las dos bitácoras los citan. Con el merge, `git log --follow` y `git blame` cruzan el movimiento.
- **Un workspace de npm en la raíz**: la API es Python y la web no comparte código con nadie; sería configuración sin uso. `marketing/` quedó en la web porque importa de `src/` y usa sus `node_modules`.
- **Un solo clon en el VPS**: el `reset --hard` del deploy de una app le cambiaría el código a la otra, corriendo y sin reiniciar. Cada app tiene su clon con sparse-checkout (`~/Vector/web`, `~/Vector/api`).
- **Fusionar la web y la API en un proceso**: reescribir 11.500 líneas de Python sin ganar nada (el salto entre las dos dura ~1 ms en el VPS).

**Estado:** el repo está armado en la rama `monorepo`. Falta el corte: renombrar `Vector-FrontEnd` a `Vector` en GitHub (conserva los secrets y los workflows), preparar los dos clones del VPS, pasar PM2 y el crontab a las rutas nuevas, mergear y archivar `FlightLog-BackEnd`.
